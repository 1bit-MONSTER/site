NPU engine#

The NPU engine runs models on the AMD NPU (the XDNA 2 NPU of the Ryzen AI MAX+ 395) on Linux, on our own runtime and kernels. It is in progress: correctness first, speed next. Its kernels, built from source, match an fp64 reference on Qwen3-0.6B, 1.7B and 4B. The layer kernel and lm head reach cosine similarity 0.9999 or better at every tested position, and greedy decoding matches the reference token for token. They are not merged into this repository yet. The release carries the NPU runtime, compiled into 1bit, and the npu backend of Lemonade's onebit recipe; until the kernels land, a release package serves GGUF models on HRX, not NPU models (Releases).

The NPU runtime and the NPU kernels are proprietary and closed source (Releases). They ship only as compiled binaries: the runtime is compiled into 1bit, and the kernels ship as compiled, encrypted artifacts that 1bit verifies and decrypts in memory at load (a wrong key fails cleanly, and nothing phones home). Their source, build and method are not in this repository or in any release. This page covers the public parts: the model format, how 1bit serve runs an NPU model, and how to build.

A model directory#

<model dir>/
  model.q4nx             weights (safetensors layout, Q4NX tiles: "Q4NX chunks" below)
  config.json            Hugging Face config: dimensions, rope_theta, eos_token_id
  tokenizer.json         Hugging Face tokenizer
  plan.json              the stream plan: fusion, kernel family, decode dirs ("plan.json" below)
  npu/                   the model's NPU kernels

1bit serve -m <model dir> serves such a directory on the NPU behind the OpenAI-compatible API (1bit serve); inside Lemonade, that is what its onebit backend runs (--onebit npu).

plan.json: the stream plan (engine #799)#

A model directory may carry a plan.json: the decisions the runtime used to make by looking at which files happened to be in --kernels. Three of them, and each one used to be silent:

decision what the probe used to do
fusion.gate_up (fused/split) the fused full_i8_GU_* kernel won, and with no split kernel on disk the split layout was assumed
kernels.tag (""/_b8/_pb16i/_t2s) the artifact family came from q4nx_weight_layout, so a kernel dir of the other family changed which kernels ran
decode.dirs the M=16 twins were looked for in <model>/kernels-m16, then <kernels>/m16, then <kernels>

tools/npu_plan.py <model dir> writes one from config.json plus the kernel directory (it derives layer roles from layer_types and projection shapes from the model's own dimensions, the way the forward does). --check re-generates and diffs against the file on disk, so a stale plan is a gate failure rather than a wrong number; --print shows it without writing.

The forward reads the plan with npu/plan/plan.h and refuses by name anything it cannot honour — a kernels.tag that disagrees with the container, a sealed ELF named outside the pb16i family, a decode dir that is absolute or contains .., a layer count that disagrees with layers[], or a kernel the plan names that is not in the directory (forward init failed: plan <path>: this model's plan needs the QKV kernel "full_i8_QKV_K1024_N4096.elf" in <dir> (missing)). A model directory without a plan keeps the probes, which is what makes this additive.

Four plans are checked in under configs/plans/, one per model directory on the build box (Qwen3-0.6B, bonsai2-27b-NPU, bonsai2-27b-NPU-b8, bonsai2-27b-pb16i); tools/npu_plan.py <dir> --check proves the directory's copy still matches. scripts/npu-window11.sh is the gate the change passed: three fixed greedy prompts and the prof table, compared between a run with the plan and a run without it (--compare A B) — 3/3 transcripts byte-identical and every prof row within 10%.

attention.mode (optional, default causal) is the mask, not a kernel decision. A pack that declares noncausal_full_attention in its own decision_config.json — a d3 readout pack, trained with every full-attention layer seeing the whole prompt — is generated as such, and the forward then encodes a prompt bidirectionally: step_batch() fills the K/V cache for every row of the batch first and only then attends, so row r sees rows after it. The GDN layers keep their causal recurrence (the pack's own runtime keeps it too), a sliding layer stays causal, and the mode reads the same numbers only in one shape:

  • the whole prompt, one batched pass, at position 0 (POST /v1/systemone does exactly that). A batch that starts above 0 is refused by name — its earlier positions were already encoded causally.
  • it cannot generate. step() (one position at a time, keys only in the past) refuses with the mode's name, so a d3 pack served on the chat route is an error rather than a silently causal answer.

An unknown mode string is a plan refusal, never a default: the two modes give different numbers, and a guessed mask is a different model.

Q4NX chunks#

Q4NX is FastFlowLM's NPU model format (MIT), and its models on Hugging Face (FastFlowLM/*-NPU2) are Q4NX directories. A Q4NX weight is a grid of 32-row x 256-column tiles, one chunk each, row-major over the grid. The chunk kind is the last dimension of the tensor's shape: [tiles, 5120], or [tile rows, tile cols, chunk bytes] (npu/q4nx.h has the byte layouts).

Chunk Kind Weight Seen in
5120 B q4_1: bf16 scale and zero per 32 columns of a row code * scale + zero Qwen3, Llama, Gemma, Phi models
4736 B Q4_K: u8 scale and min per 32 columns, bf16 S, M per row S * scale * code + M * min Qwen3.5-4B projections
8704 B Q8: bf16 scale per 32 columns, int8 codes d * code Qwen3.5-4B lm_head and embedding
2176 B t2: 2-bit ternary codes, one fp16 scale per 128 columns of a row code * scale ternary models (Bonsai-2, PTQ1_0/TQ1_0 sources)

Q8 has two code layouts under the same chunk size. Qwen3.5-4B's lm_head (tied to the embedding) stores code (row r, column k) at byte k*32 + r. Qwen3.6-35B-A3B's Q8 tensors (untied lm_head, projections) store it at (r/16)*4096 + (k/32)*512 + (k%32)*16 + r%16. Both containers report flm_version 1.0.3, and neither carries metadata that tells them apart. Decoding tile (0, 0) of each lm_head and comparing with a GGUF of the same model gives correlation 0.9998 with the right layout and about 0.01 with the other. npu/q4nx decodes the first layout.

npu/q4nx.h decodes all four, and repacks Q4_K into q4_1 (exact apart from rounding S * scale and M * min to bf16), so code that reads q4_1 runs Q4_K weights unchanged. Q8 does not fit q4_1, and neither does t2 (per-128 fp16 scale against q4_1's per-32 bf16 one): a t2 tensor is expanded on the target, never repacked. tests/npu_q4nx_test.cpp checks the decoders bit for bit against reference decoders on real Qwen3.5-4B and Qwen3-0.6B tiles (committed in tests/golden/q4nx), and the repack against its rounding bound; t2 has its own contract test (tests/npu_t2_layout_test.sh) and oracle (tests/q4nx_t2_test.py).

The t2 chunk kind#

A ternary model stores every weight as code * d with code in {-1, 0, +1} and one d per 128 columns of a row. t2 is that, in the same 32x256 tile grid as every other chunk, at 2.125 bits/weight — the stream a 27B ternary model is meant to be read at, instead of the 4.5 b/w pb16i image (int4 codes + one int16 magnitude per 32 K) that the exact path streams today.

t2 tile, 2176 bytes, 32 rows (N) x 256 columns (K) of one tensor
  [0, 2048)     2-bit codes:  byte r*64 + c/4, code c%4 at bits 2*(c%4)
                value 0 = -1, 1 = 0, 2 = +1, 3 = reserved (no converter emits it)
  [2048, 2176)  IEEE fp16 scales: half at 2048 + r*4 + 2*g,  g = c/128
                                                        w[r][c] = code * scale

Tile order is the container's everywhere: row-major over the [N/32][K/256] grid, so one 32-column block's whole K extent is contiguous. Geometry: N % 32 == 0, K % 256 == 0.

A tensor that is not whole tiles is padded, not refused-and-forgotten. The padding is code 0 with scale 0.0, i.e. a weight of exactly 0: a padded K column contributes 0 to the reduction whatever the activation is, and a padded N row is never read. tools/q4nx_t2.py refuses such a tensor by default and pads it with pad=True (pad_to_tile). The chunk has no field for the original shape, so the padded shape is the tensor's shape and the consumer skips the rows the writer did not fill. All 431 ternary Bonsai-2 images are already whole tiles (5120 / 6144 / 17408-column rows), so this exists for GGUF tensors and for any projection whose width is not a multiple of 32.

The stored weight is the folded (post-rotation) one, and t2 carries no rotation of its own. A folded container's W' already has the block Hadamard and the per-width signs baked into the weights; the consumer rotates the activation into that basis — A' = H (A . s), signs first, then the normalized Sylvester-Walsh butterfly, then the 1/sqrt(block) — and never touches the weight (npu/forward/include/hadamard.h, called from q4nx_forward.cpp). So a t2 tensor holds W' exactly as the pb16i image does, the fold declaration stays where it belongs (the container's q4nx_hadamard, q4nx_hadamard_block and the HAD1 sign table), and the chunk needs no pre/post-rotation flag: reading a t2 tensor in the wrong basis is a consumer bug, not a format one. The inverse direction (the tied embedding, inverse_weight_names in the pack) is S (H y), which round-trips to the identity.

This rotation is host work on the critical path, so it is SIMD, and it must stay bit-identical. It runs once per projection — ~430 times a decode token on Bonsai-2 — and the scalar butterfly cost 14.2 us per 5120-float vector in-loop: 15.8 ms/token in a quiet window and 39.0 ms/token on a loaded one, i.e. pure CPU contention that a device-side win cannot touch. hadamard.h keeps the scalar loop as the reference and adds an AVX2 path (dispatched at run time) that performs the same adds and subtracts on the same operands in the same stage order — stages 1, 2 and 4 as an 8-lane in-register butterfly, every later stage as contiguous 8-lane add/sub — so the rotated vector is bit-identical and no container's text moves: 7.6 -> 2.4 us per 5120-float vector, 40.0 -> 16.8 us per 17408-float one. tests/hadamard_rotate_test.cpp is the gate that runs on every build, on any host: bit-for-bit equality against the scalar loop for every block a container can carry and for the fleet's real activation widths, plus a check that the scalar loop really is the Hadamard transform (compared against a direct sum over the sign pattern).

The scale is fp16, not bf16, and that is load bearing. Every source format already stores this scale as fp16 — PTQ1_0's, TQ1_0's and TQ2_0's d are ggml_half, and pb16i's ms * 2^e_ref is an int16 with a per-column exponent — while bf16 has 8 significand bits against fp16's 11. Measured on the 431 ternary Bonsai-2 images (416 layers + the 15 MTP head tensors, 25.66 G weights): 174,982,781 of 200,499,200 scales (87.27 %) are not bf16-representable, worst relative error 3.89e-3; fp16 is exact on all 200,499,200. fp16 and bf16 are both two bytes, so asking for bf16 buys nothing and costs the bit-exact gate. A target whose arithmetic wants bf16 converts at load, in the kernel, and owns that rounding — the chunk keeps the exact value.

A reserved code (3) decodes as 0, on both paths — npu/q4nx.cpp::dequant_tile and tools/q4nx_t2.py::unpack — so a corrupt byte cannot become a weight no converter wrote, and it can never be a 2 * scale value that no ternary encoder can produce. No converter emits one; q4nx::t2_reserved() counts them, and that is what a loader or a test refuses on. (An all-zero code byte is code -1, not code 0 — the value table is code - 1, the same convention Q2_0 uses.)

what measured
ternary codes in the 431 images all {-1, 0, +1}, no reserved pattern
one scale per 128 K is enough (the four per-32 magnitudes agree) 100 % of blocks
fp16 scale exact vs the pb16i floats 200,499,200 / 200,499,200
27B size pb16i 14.44 GB -> t2 6.82 GB (416 layers 6.46 GB, 15 head tensors 0.36 GB)
2.125 b/w 2176*8/8192 exactly

The oracle is bit-exact, not approximate: tools/q4nx_t2.py from_pb16i refuses anything it cannot represent exactly (a non-ternary code, magnitudes that differ inside a 128-K block, a scale that is not fp16-exact), and tests/q4nx_t2_test.py re-decodes the result and compares against the pb16i dequantisation of the same image, float for float, on all 431 images when they are on the machine. Converters: from_pb16i (the engine's integer-exact image), from_ptq1_0 and from_tq1_0 (both ternary with an fp16 scale, lossless). from_tq2_0 is refused unless asked, because TQ2_0's code 3 means +2 — it is not a ternary format, and clamping it to +1 changes weights.

The t2s stream (what the XDNA decode kernel reads)#

t2 is the container format: the decoder's byte order, for any consumer. The device does not want that order — the mmul takes int4 nibbles at element e = r*16 + c of a 16x16 block in byte e/2 — so the kernel would have to transpose 2-bit codes across lanes. tools/q4nx_t2s.py derives the stream form of the same weights instead, which makes the on-core expansion a byte-local 1 -> 2 map:

2,176 B per k=256 x n=32 tile, 2.125 b/w (pb16i 4,608 B; 27B 14.44 GB -> 6.82 GB)
[0, 2048)    2-bit codes, n-major blocks: block (nb, kb) at (nb*16 + kb)*64, and inside a block
             byte r*4 + j holds the four codes for k = kb*16 + r, n = nb*16 + 4j + {0,1,2,3}
[2048, 2176) int16 multiplier per 128-K block per column, [nb 2][gb 2][16 c] -- pb16i's own `ms`
             at the granularity the model stores (pb16i repeats it 4x to reach 32-K granularity)
expansion: out[2i] = f(c0) | f(c1)<<4, out[2i+1] = f(c2) | f(c3)<<4, f(v) = v - 1 mod 16 = {15,0,1}

The stream's contract is byte-exact against the image it came from, not statistical: expand() must reproduce the pb16i code bytes block for block (and stream()/from_pb16i_image() must agree byte for byte), which tests/q4nx_t2s_test.py checks synthetically and which was also run on the real Bonsai-2 images (all 10,880 tiles of blk_0_ffn_gate_weight.pb16i, 0 of 44,564,480 code bytes differing, 14.44 GB -> 6.82 GB — the same 6.82 GB the t2 chunk reports). from_pb16i_image refuses, with a named error, an image whose four 32-K multipliers inside a 128-K block are not equal: that is the one thing this compaction cannot hold, and it is the thing the t2 chunk's own gate measures at 100 % of blocks for Bonsai-2. The n-major order also makes one nb (1,024 B) a single contiguous DMA run, and the tile itself is streamed as one 2,176-B run: 2-bit must not cost contiguous-run length.

A model shipped in the t2 form needs no pb16i image to feed this kernel: from_t2(chunk, K, N) takes the container's own chunk and returns the same bytes from_pb16i_image() returns for the image it was made from, by re-deriving the image with the packer's code rather than a second implementation of the tile order. The two forms are the same weights in different orders (t2 is k-major within each 32-row band, t2s is n-major within each 16x16 block: on the test fixture's 139,264 stream bytes, 135,476 differ), so they are never interchangeable and from_t2 is the only crossing — the test asserts both the equality and that inequality, so a "simplification" that returns the chunk unchanged fails.

Wire format v2: the ordering moves into the stream, not the core#

The mmul's operand byte for element e = 16k + c is e/2, so a 64-byte vector of 2-bit codes has to reach the operand's even bytes and the next 64 its odd bytes — a spread, not a copy. Under the original order (v1) that spread is a lane-crossing shuffle inside the core (aie::interleave_zip), and it was measured on the array: 11.1-12.6 GB/s against 30-32 GB/s for the plain contiguous stores with the wrong order. So v2 changes the order inside each 64-byte block and nothing else:

v1: byte r*4 + j  ->  k = kb*16 + r,        n = nb*16 + 4j + {0,1,2,3}
v2: byte b        ->  lanes 0/1: k = kb*16 + b/8,     n = nb*16 + 2*(b%8), +1
                      lanes 2/3: k = kb*16 + 8 + b/8, n = nb*16 + 2*(b%8), +1

which is exactly the arithmetic the operand wants: byte b of the first store covers element 2b = 16*(b/8) + 2*(b%8), and byte b of the second store covers 2*(64+b) = 128 + 2b, i.e. eight k rows down. The kernel's two contiguous stores are then correct with no shuffle and no table — the same kernel binary that had to interleave is byte-exact on v2 (3/3 seeds, 0 mismatches, amdxdna counter 0, measured 2026-11-02). The tile is still 2,176 B and the time order is unchanged, so the DMA descriptors and the tile count do not move; the ms area is byte-identical between the formats.

tools/q4nx_t2s.py carries both: from_pb16i_image()/stream()/decode()/expand() are v1, from_pb16i_image_v2()/decode_v2() are v2, and tests/q4nx_t2s_test.py pins that they carry the same codes and the same multipliers, that only the code area differs, and the block algebra above. A container declares which one its images are with q4nx_weight_layout_version (5 = v1, 6 = v2): the two are not interchangeable — a v1 image read by the no-shuffle kernel is a silent permutation of the weight matrix, which is precisely the failure that took three single-code probes to name.

The t2s stream in the engine (launch path)#

A container streams t2s when its config.json says "q4nx_weight_layout": "t2s" (pb16i is 4, and each layout refuses the other's version). The version picks the artifact family, because the two t2s wire orders hold the same weights at the same size in a different byte order and reading one with the other's kernel is a silent permutation of the matrix, not a crash: 5 = v1 -> _t2s / _t2s_m16 (the expansion interleaves inside the core), 6 = v2 -> _t2s2 / _t2s2_m16 (the ordering is in the wire, so the core's two contiguous stores are exact — no lane shuffle), and any other version is refused by name at init. v2 is the one to ship: measured on the array for GU (K=5120 N=17408, M=16) against the pb16i phase in the same window, 0.589 ms vs 1.037 ms (1.76x), 40.2 GB/s of stream against 48.4, with seeds 1/2/3 byte-exact and the amdxdna counter 0 (~/wt/npu-arena/LEADERBOARD.md, submissions/GU16T2S). The images are the pb16i sidecars' own set — blk_<layer>_<tag>_weight.t2s plus the unchanged .ref (e_ref int16[N] + mode byte, because the compaction changes neither the magnitudes nor e_ref) — in the directory named by q4nx_t2s_dir / Q4NX_T2S_DIR, and the kernels carry the _t2s suffix (full_i8_GU_K5120_N17408_t2s.elf, and the _t2s_m16 decode family). tools/q4nx_t2s.py writes those files from either form of the same weights — from_pb16i_image() for a container that ships pb16i sidecars, from_t2() for one that ships only t2 chunks ("derive the t2s stream from a t2 chunk, so the container is enough", #830); nothing is requantised in either crossing.

Everything downstream of the load is pb16i's path: the same int32/int64 accumulation, the same host-side single rounding, the same per-column 2^e_ref, and the same loud refusals. The one difference the host must respect is the file: q4nx_t2s.h gives the 2,176-B tile, and a .t2s file that is not tiles x 2,176 bytes is refused by name (never read as a pb16i image). Two independent checks keep the contract honest without a device: tests/npu_t2s_layout_test.cpp pins the tile against the numbers the tool measured on a real image (gate/up: 50,135,040 B of pb16i → 23,674,880 B of stream), and tests/q4nx_t2s_test.py pins the code order byte for byte.

A t2s container wants a sealed set for the same reason a pb16i one does. The layout is not what makes a phase change expensive: the hw_context is. Measured on this box in-loop on 2026-11-02, a t2s decode family shipped as eight per-role _t2s2_m16 ELFs paid +2.0-2.3 ms on every launch, in every role — more than the kernels' own device time — against the ~2.7 ms between two hw_contexts recorded at npu/forward/include/q4nx_forward.h. That tax turned a kernel that is 1.76x faster in the arena into a model that was 1.8x slower than pb16i. The fix is the same artifact shape pb16i uses: one full ELF carrying every instance (main:gu|d|qkv|o|z|qh|kv), named by the container's own key q4nx_t2s_sealed_elf (pb16i keeps q4nx_pb16i_sealed_elf; a layout never borrows the other's key, because a pb16i ELF would read 4,608-byte tiles out of 2,176-byte images). tools/npu_plan.py writes the key into plan.json's decode.sealed_elf, and the engine runs every decode role inside that one context.

From a GGUF#

tools/gguf_to_q4nx.py pack <model.gguf> <out dir> --tokenizer <dir> writes a model directory's model.q4nx and config.json from a GGUF (qwen3, qwen3moe and qwen2 for now), and copies tokenizer.json from --tokenizer. It writes every projection and lm_head as q4_1 tiles and the norms and embedding as bf16. A tied lm_head is made from token_embd. A MoE model's router stays bf16 and untiled (it runs on the host, and its top-k must be the GGUF's own), and its routed expert stacks become one tensor per layer and projection — see "Routed expert stacks" below.

GGUF type To q4_1 Error
Q4_0 scale d, zero -8d, codes unchanged bf16 rounding of scale and zero
Q4_1 scale d, zero m, codes unchanged bf16 rounding of scale and zero
Q4_K per 32-column sub-block: scale d*sc, zero -dmin*mn, codes unchanged (a Q4_K super-block is one tile row's 256 columns) bf16 rounding of scale and zero
Q5_K, Q6_K, Q8_0, F16, BF16, F32 dequantized, then min/max q4_1 per 32 columns lossy

tools/gguf_to_q4nx.py verify <model.gguf> <out dir> decodes every tensor it wrote and compares it with the GGUF, dequantized. For the exact types, every weight must lie within the bf16 rounding bound. The requantized tensors show their error.

On Qwen3-0.6B-Q4_K_M.gguf (unsloth), all 311 tensors pass. The Q4_K tensors have 0 weights over the bound. The Q6_K tensors (half of v_proj and down_proj, and lm_head from the Q6_K embedding) requantize to cosine 0.9969 and relative RMS error 0.079. Served on the NPU, the repacked model decoded 24/24 greedy tokens the same as a CPU reference of the repacked weights, with every step's logits at cosine 0.99995 or better.

Routed expert stacks#

A MoE GGUF keeps its routed experts as one three-dimensional tensor per projection (blk.N.ffn_{gate,up,down}_exps, ggml [cols, rows, experts]), expert e on rows [e*rows, (e+1)*rows) of the stream. The converter writes each stack as ONE container tensor — model.layers.N.mlp.experts.{gate,up,down}_proj.weight, I8, shape [experts * rows/32, cols/256, 5120] — so expert e is tile rows [e*rows/32, (e+1)*rows/32) of a plain tile grid: a decode step points a kernel at one expert's 192 chunks (983,040 B on Qwen3-30B-A3B) without any gather.

model.q4nx's __metadata__.moe carries that decomposition so a caller never derives it: experts, used, norm_topk_prob, and per tensor rows, cols, tile_rows, tile_cols, tiles, bytes and the byte offset of every expert (offsets, [experts] entries, relative to the data section like every data_offsets). Those offsets are the list a per-dispatch chunk-address kernel takes (docs/npu.md, the DMA path in the engine's NPU lane).

Measured on Qwen3-Coder-30B-A3B-Instruct-Q4_K_M.gguf (qwen3moe, 48 layers, 128 experts, top-8, expert_ffn 768, no shared expert): 579 tensors, 144 expert stacks x 128 expert offsets, header 302,144 B, container 19,528,322,120 B (18.19 GiB) — 18.13 GiB of it routed experts.

The top-8 boundary is razor thin. Measured with the same router tensor on the same token, the container's weights against the GGUF's own f32 weights: 32 of 48 layers pick a different 8-expert set, always at the 8th slot, because the margin between rank 8 and rank 9 is 1.2e-3 in probability in one and 2.9e-4 in the other (layer 2: expert 25 at 0.021700 vs expert 125 at 0.020511, and the reverse). A hidden state that differs by 0.5 % — what requantising the Q6_K tensors costs — is enough to swap it.

That is a symptom, not the whole story, and the difference matters when judging a kernel. Re-running the same comparison with the container's routing pinned for the f32 pass — same expert ids and weights at every layer of every position — the log-prob difference does not shrink at all (mean |dlogp| 14.36 nats pinned against 14.29 unpinned, over 16 teacher-forced positions). So the routing flips are not what separates the two weight sources; the per-layer hidden state (cos 0.993-0.9996) compounding through 48 layers is, and it changes which token wins a peaky position. Two things follow, and they are the operative rules here: compare implementations on aggregate quality (KLD over a corpus, perplexity), never single-token argmax or per-token log-probs; and gate a kernel with the expert ids held fixed (A row + the router's own top-k + the expected int32 per expert, which is what tools/moe_expert_chunks.py gate emits), so the gate measures the kernel and not the model's own sensitivity. verify result: see the TMOE-NPU lane's state file.

1bit serve -m <model.gguf> --device npu repacks a GGUF itself, caches the result under ~/.cache/1bit/q4nx/, and serves it. The repack runs the engine's own scripts/repack_gguf.py, which the package ships beside 1bit (scripts/, with its declared-scale guard; ONEBIT_Q4NX_REPACK overrides the path), so a packed install repacks too. It needs python3 with numpy and gguf, and FastFlowLM's Q4NX converter, which is not vendored: point ONEBIT_Q4NX_CONVERTER at a converter checkout (a ~/np-model-generic beside the engine or in the home directory is found without it). GGUFs of six architectures (Qwen2.5, Qwen3 MoE, Qwen3.6-35B-A3B, MiniCPM4/5, GLM-4.7-Flash) answer correctly this way, on a generic per-op path that is not yet fast (#179, #181, #209). On a release, GGUFs belong on HRX.

Declared scales are checked. The repack (scripts/repack_gguf.py) fails with rc=1 if the GGUF declares a known-critical scale-like value that the repacked config.json drops: embedding_scale, residual_scale, logit_scale, scale_emb, scale_depth, dim_model_base, final_logit_softcapping, attn_logit_softcapping. MiniCPM4-8B decoded punctuation soup because three of them were dropped, and no argmax-level check can see the third, which moves only the probabilities. Any other scale-like key (*scale*, *softcap*, *mup*) is warned about, not fatal. scripts/check_repack_config.py runs the same scan on its own, with a negative control.

A cached directory is checked again on every hit, with the same metadata-only scan, and it is rebuilt if the scan fails or if its repack-stamp.txt (converter path and commit, architecture, repack script) names a different converter than this build would use (repack_gguf.py --check-stamp <dir>: exit 0 current, 1 stale, 2 cannot tell). If the checker or the converter cannot be found, serve warns once per process and reuses the directory, so a missing script cannot stop serving. A Q4NX directory served as it is (1bit serve -m <Q4NX dir>), such as a published FastFlowLM model, is trusted as published. Its chunk layout can be checked first, without dequantizing anything: tools/check_q4nx_dir.py <dir> reads the container header only, names each quantized tensor's chunk kind, and refuses an unknown chunk size or a tensor shorter than its layout needs. It cannot tell the two Q8 layouts apart ("Q4NX chunks", above), because the container does not record which one it holds.

From a Ryzen AI OGA NPU pack#

1bit npu-pack import <pack dir> -o <out dir> reads a pack AMD publishes for Ryzen AI (*_rai_*_npu_*: model.onnx, model.onnx.data, dd_metastate_*.fconst, config.json, genai_config.json, the tokenizer) and writes a model directory. 1bit npu-pack info <pack dir> prints what the pack states as JSON and writes nothing. The pack's weights and its config/tokenizer contract are the model; the reader is written from the pack-side facts in amd-oss/npu-re/docs/FACTS-oga-pack-weight-layout.md, and no vendor library, wheel or compiled program is called or shipped.

An OGA pack keeps its tensors inside the If branches: the top-level graph has no initializers and four nodes (Shape/Constant/Equal/If). The importer walks the subgraphs. The 4-bit decode is w = (code - zp) * scale with two codes per byte (low nibble = even k) and two zero points per byte; that decoder is checked against the pack's own data, because tie_word_embeddings makes dequant(lm_head) reproduce the fp16 embedding:

corr 0.999999, relative error 0.00070 on all 151936 x 896 weights
controls: nibble-swapped corr -0.0008, no zero-point corr 0.8788   (both rejected)

Two facts bound what the container can hold, and both are reported, not hidden:

  • A bf16 zero does not always hold a f32 one. A q4_1 chunk stores bf16 scale and zero. This pack's scales are already bf16 values (0 % rounded), but -zp*s is bf16-exact for only 43.5 % of 32-column groups. The residual is that rounding: 3.34e-3 relative, 2.4e-4 absolute on the dequantized weights, with no code moved. Read back through q4nx::dequant_tile the container matches the pack to that bound.
  • K is padded to the 256-column grid. Qwen2.5-0.5B has hidden 896 = 3.5 tiles, so lm_head and q/k/v/o are stored as 4 column tiles with the last one zero-padded (codes 0, scale 0, zero 0). That is 12.5 % more bytes than the pack; the true K is in the container's manifest and in config.json, and nothing reads a padding column as a weight.

The .fconst attention payload#

A layer block's attention payload sits between its two epsilon headers and is a whole number of 64-row tiles: one tile is 2*(K/128) + 2 subvolumes of 2,176 B, a pair per (column half, K block of 128) plus the pair the writer puts its bias input in. Inside a weight subvolume, [0, 2048) are the quants (byte (cp%4) + kk*4 + (cp/4)*512 holds rows 2*cp and 2*cp+1 at column kk of the block), [2048, 2064) the zero points and [2112, 2176) 32 bf16 scales, one per row of the half. Codes and zero points are int4 in two's complement; the +8 an ONNX MatMulNBits adds cancels between the two fields, so the stored nibbles are used as they are. FACTS §7.13 established that layout by known-answer write and §7.15 against shipped bytes.

Which tile belongs to which projection is measured, not assumed: on the shipped 0.5B pack the tiles' bias subvolumes matched the pack's own q/k/v bias vectors, which identifies the runs as k (2 tiles), q (14), v (2), o (14) — 32 tiles, the payload's whole size. A pack whose payload is not a whole number of tiles of that hidden size, or whose q/k/v/o row counts do not add up to the measured tile count, is refused by name with the numbers (npu-pack info reports the measurement).

Every tile read is its own check. Before anything is written, each tile is decoded and re-encoded; the encoder has to reproduce the 34,816 bytes it came from, bias slots included. That one comparison holds every field, index and nibble order at once, and it is why a tile whose fields we do not understand cannot be imported silently: on Qwen2.5-0.5B-Instruct_rai_1.8.0_npu_4K it passes 768/768 tiles of 24 layers. tests/golden/oga_attn_tile.bin is one of those tiles, copied verbatim from the pack by tools/oga_attn_tile_golden.py, so the same check runs in CI against the vendor writer's bytes with no vendor stack present. The fixture's identity is independent of this reader: the vendor packer (matmulnbits_pack_const_float32, mladf_version v2) reproduces the shipped tile from the arrays this decoder produces.

Refusals are named, and a refusal writes nothing. Without --allow-incomplete, a pack the importer cannot represent exits 3 and lists every tensor it refused with the reason, so a partial model never lands in a model directory by accident. With --allow-incomplete it writes what it can and records the rest in the container's __metadata__ (incomplete) and in config.json (q4nx_source.incomplete). On the shipped Qwen2.5-0.5B-Instruct_rai_1.8.0_npu_4K that is now 218 tensors, 25,136 tiles (embedding, head, 48 layer norms, 96 attention projections, 72 attention biases) and 73 refusals: the 24 x 3 MLP projections, whose section of the .fconst is 16 subvolumes of 4,288 B per 128-row unit (64 output rows per column group, i.e. the vendor writer's Nsubv 64 instance) carrying one fused gate/up tensor whose rows interleave in 32-row chunks — the unit size and the interleave are established from the writer's own headers, the intra-subvolume byte order is not, and the packer this importer checks against emits only the 2,176-byte instance for K=896, so those tiles cannot be re-encoded and byte-verified the way the attention tiles are; and the final norm, whose 1,856-byte tail envelope turned out to be [eps][pad][448 f32] and not an RMSNorm weight on either .fconst.

The norms that are imported sit at the documented offsets, each confirmed by the epsilon that opens its layer block: 48/48 anchors found. tests/npu_pack_import_test (registered as npu_pack_import, and as npu_pack_import_oga when -DONEBIT_OGA_PACK=<dir> is given) checks the decode, the tiling against tests/golden/oga_pack_tiles.bin — written by tools/oga_pack_tiles_golden.py with the same layout tools/gguf_to_q4nx.py has always used — the attention tile against tests/golden/oga_attn_tile.bin, and, against a real pack, the refusal list, the tile round trip, the self-check numbers and that the container opens with npu::Model.

Cross-check against the official converter#

ROCm's FLM_Q4NX_Converter (convert.py) is the official gguf → Q4NX converter, and since 2026-10 it is public and Apache-2.0; scripts/repack_gguf.py already drives it for the 1bit serve --device npu repack path. It was run against tools/gguf_to_q4nx.py on the same GGUF (Qwen3-0.6B-Q4_0ctl.gguf, qwen3, 311 tensors: 196 Q4_0 projections, Q8_0 embedding and lm_head, F32 norms) and both containers were byte-compared tile by tile (tools/q4nx_diff.py compare) and decoded back against the GGUF (tools/q4nx_diff.py decode). Tensors: 114 of 311 byte-identical (the bf16 norms and embedding), 197 differ.

The container format is the same; the payload is not. Same tensor names, dtypes (I8 / BF16), shapes and tile geometry (32x256, 5120 B = 512 scale + 512 min + 4096 codes), and model.q4nx headers differ only by this engine's 104-byte __metadata__ block — the official output's header is byte-size-identical to the shipped Qwen3-0.6B-NPU2 container. The tiles differ because the two encodings are different, both exactly:

this engine (npu/q4nx.cpp) official converter
Q4_0 zero-point in the min plane, -8d min plane is 0
Q4_0 codes unsigned q (0..15) signed q-8, nibble = q xor 8
code order in a tile [row-half(2)][group(8)][col-in-group(32)][row-pair(8)] (the 16-row split the kernel walks) plain column major [col(256)][row-pair(16)]

Measured, per tensor, against the GGUF as ground truth: 196/196 Q4_0 tensors exact (0.0 error) under each file's own decoder — so both converters are correct — and 0/197 exact when one is read with the other's decoder (worst error 2.8-3.0). The scale planes of all 53 760 Q4_0 tiles are byte-identical; every min byte and every code byte differs. A container written by one converter must not be fed to the other's decoder: this engine's ELF route decodes the former layout only, which is also why npu/model.cpp and tools/q4nx_to_gguf.py refuse a container whose provenance they cannot establish.

The one place both are lossy is the Q8_0 lm_head: neither keeps it at 8 bits, both requantize to a 5120-byte tile. This engine's packer does it deliberately per 32 columns (max error 1.65e-2, rms 2.28e-3 against the source); the official path runs the 8-bit codes through its 4-bit packer (max error 3.23e-1, rms 2.94e-2, ~13x worse).

Two divergences worth knowing before packing a GDN model: the official qwen3.5_* configs carry a per-tensor dtype table (Q4_K default, ssm_out_proj Q4_K, alpha/beta Q8_0, lm_head Q8_0, norms BF16), prefill-mode .bf16 twins for ssm_alpha_proj/ssm_beta_proj, an (q g) -> (g q) reorder with q=2 for ssm_a and ssm_dt.bias, parallel_size 32 and keep_block_in_2D true. tools/gguf_to_q4nx.py has none of that (it is qwen3-only, parallel_size 16 semantics), so a hybrid-GDN model — including this engine's 27B — cannot be packed by it yet; the official configs are carried as data in configs/q4nx/ so that gap is described rather than guessed at.

tools/gguf_to_q4nx.py pack now also looks for tokenizer.json beside the GGUF when --tokenizer is omitted, and warns loudly when it is still missing: a directory without it is not servable, and the tool used to report success anyway.

Serving#

The 1bit NPU engine runs the model on the XDNA 2 NPU. With a release package that carries the NPU kernels (dense Qwen3: 0.6B, 1.7B and 4B):

./1bit serve -m <Qwen3 NPU model dir> --port 8000

In Lemonade, the onebit recipe's npu backend serves the same directories (--onebit npu). The model directory holds the weights only; the kernels ship inside the package.

Sealed kernel sets: the manifest is what says a set is ours#

A set ships as <set>/layout.json, <set>/layer1_*/layer1.elf (each 1BPKCRYP ciphertext, opened in memory by the loader with the kernel key) and two more files: manifest.json, which lists every file the set carries with the sha256 of its ciphertext, and manifest.sig, an Ed25519 signature over the manifest's exact bytes made with the release signing key. Sealing on its own is confidentiality only: a set re-sealed by another key, or swapped for a different set that also decrypts, would be indistinguishable from ours. The signature covers the manifest, the manifest's digests cover the ciphertext files, and the release public key never leaves the loader.

tools/seal_manifest.py is the public half: write <set> --key <release key> emits both files, check <set> proves the manifest lists exactly the set's files with their sha256 (no key needed), and verify <set> --pub <release public key> proves the signature too. scripts/package-linux.sh refuses to pack a set without them, scripts/weekly.sh's package_checks refuses a tarball whose sets do not match their manifests (ONEBIT_SEAL_PUB=<release public key> also verifies the signatures there), and 1bit-release-check's sealed/sealed-sig rows prove the same on the stick (the signature where the image has an interpreter and the key). The loader-side requirement, ONEBIT_KCRYPT_REQUIRE_MANIFEST=1 beside ONEBIT_KCRYPT_REQUIRE_SEALED, is read by the private NPU runtime and lands with the pin that makes it honour one - engine #574.

The dense FFN tail cache (hybrid GDN models)#

On a GDN model the guard that skips the per-token Q4NX dequant in step() can never fire (dense_weights_cached requires lin_kd_ == 0, and lin_kd_ is model-level), so a hybrid model re-dequantised each layer's 17408-wide dense FFN tail on every token even after those weights were packed on the device. ffn_tail_cached() (npu/forward/src/q4nx_forward.cpp) closes that: once a layer's packed gate/up/down BOs are resident, the f32 wg_/wu_/wd_ buffers are no longer read, so the reload is skipped. It is on by default for a GDN model on the NPU route, when the packed weight cache is on, the run is not NPU_INFER_HOST_GEMM, and the tail is at least 256 MB per layer (the size guard; below that the reload is too small to be worth a behaviour change). NPU_FFN_CACHE=0 or =1 forces it either way, and the resolved state is logged once as [ffn] dense-tail cache on|off (default|NPU_FFN_CACHE; lin_kd=… IM=… H=…). On Qwen3.8-27B-NPU2 an interleaved 5-round A/B (~/lb/587-cache-20261030) measured an 8-token request at 104.5 s against 117.4 s (−11%), CPU per token 22.9 s against 63.3 s (−64%), same text in every arm.

Sampling and structured output#

1bit serve -m <NPU model dir> --device npu serves through 1bit forward-serve (app/forward_serve.cpp) in the same process. Every field below is optional, and the answer is greedy when none of them is sent, so a client written before them gets the same text it got before.

Request field Meaning
temperature 0 or absent decodes greedily (argmax); above 0 divides the logits before the draw
top_k keep the k highest logits; 0 or absent keeps all of them
top_p nucleus sampling, 1 or absent keeps all of them (min_keep candidates always stay)
seed the same seed and the same request give the same text; absent or -1 seeds from the clock
logprobs true reports each generated token's log-probability on /v1/chat/completions (streamed or not); the values are the raw distribution, before top_k/top_p/temperature and before any grammar mask, as OpenAI and vLLM report them
top_logprobs 0-100 alternatives per token, highest raw logit first; needs logprobs: true
stop up to 4 strings: generation stops before the first match, and the tail is held back so a stop split across two tokens still matches
chat_template_kwargs {"enable_thinking": false} makes the assistant turn start with the empty <think>\n\n</think>\n\n block Qwen3's own template emits, so the answer goes to content instead of into a <think> block (and its tokens get logprob entries). Default true; a non-boolean is a 400
grammar a GBNF grammar in llama.cpp's format (third_party/llama.cpp/grammars/*.gbnf) the answer cannot leave
response_format {"type": "json_object"} constrains the answer to JSON; {"type": "json_schema", "json_schema": {"schema": …}} constrains it to that JSON Schema

logprobs keeps OpenAI's shape: non-streamed, every entry is choices[0].logprobs.content[i] = {token, logprob, top_logprobs: [{token, logprob}]}; streamed, each chunk carries the entries whose bytes that chunk carries, so the deltas add up to the non-streamed reply. Token text that is half a character is reported with the invalid bytes replaced, never as a failed request. Entries exist for content tokens only: a reasoning delta and tool-call markup get no logprobs entry, because app/npu_answer_parser.h says where the content boundary is. On a Qwen3 model that means a thinking reply reports none at all, which is why chat_template_kwargs.enable_thinking: false is what a logprob comparison wants. The /v1/completions route's legacy logprobs object is not implemented and asking for it there is a 400, not a silently dropped field.

json_schema is compiled to a grammar before the first token, by app/npu_json_schema.h, so the answer cannot leave the schema while it is being written rather than being validated afterwards. The covered subset is OpenAI's structured outputs: objects (properties, required, additionalProperties: false), arrays (items, minItems, maxItems), string, number, integer, boolean, null, a type list such as ["string", "null"], enum, const, and oneOf/anyOf as alternation. Anything outside it (pattern, format, minimum/maximum, $ref, allOf, …) is a 400 that names the keyword: a constraint quietly dropped from a schema would leave the caller believing the answer was validated. Properties are generated in the schema's order with the required ones first, so the object's key order is fixed for a given schema.

A field the route cannot honour is a 400 whose error.message says why ("json_schema: pattern is not supported by this route's schema-to-GBNF converter", "gbnf: unterminated literal at line 1"), never a silently ignored key. finish_reason is length when max_tokens ran out, and stop for an end-of-sequence token, a stop sequence or a grammar that allows nothing more.

The sampler is llama.cpp's, without llama.cpp: app/npu_sampling.h repeats the semantics of third_party/llama.cpp/src/llama-sampler.cpp (top_k, then top_p, then temperature, then the cumulative-sum draw that common/sampling.cpp's chain ends with) over the raw logits this route has, because llama.cpp's sampler needs a llama_context and a llama_vocab and the forward has neither. The grammar (app/npu_grammar.h) is the same rule model - one flat element vector per rule, ALT/END between alternatives - as a byte-level pushdown automaton: a token is only sampled when its decoded text leaves the grammar alive, which is checked per token against the byte ranges the grammar can continue with. Both headers are device-free, and tests/npu_sampling_test.cpp runs the sampler, the parser, the JSON grammar, the schema converter and the request parser in CI without a model or an NPU.

Decisions (/v1/systemone, issue #653)#

A Decision 3.0 (d3) pack does not generate text: you send a state and one or more questions and get a probability for every option. When the model directory carries the pack's decision head, 1bit forward-serve serves that too, from the same process and the same weights:

<model dir>/model.q4nx            the Qwen3.5 GDN backbone, as any other model
<model dir>/decision_config.json  the pack's codes, token ids, temperature, pooling
<model dir>/decision.q4nx         the readout, [codes, hidden] F32 (tools/safetensors_to_q4nx.py decision)
route meaning
POST /v1/systemone (alias POST /v1/decisions) {"state": …, "questions": {id: question}} → {"model", "answers": {id: answer}, "usage"}
GET /v1/systemone/models the decision model this build serves: name, description, max_input_tokens, modalities

questions is an object, and its ids come back as the keys of answers in request order. Question types are choice (1–255 options), noul and score (2–10 ordered levels); a decision runs one backbone prefill per question, pools the last position's hidden state after the final norm (pooling: last), multiplies it by the readout and takes a temperature softmax over that question's options. Nothing is sampled and nothing is generated, so usage.output_tokens is always 0 and input_tokens is the sum of the answered questions' prompt lengths.

The prompt is the pack's own contract, not this route's ChatML: npu/systemone.h renders the State:/Question:/Options: turn byte for byte from the pack's d3_format.py (checked against fixtures it generated, ctest systemone_contract), and app/npu_systemone.h wraps it in the pack's chat template with enable_thinking=False — which opens the assistant turn with an empty think block. Those trailing bytes are part of what the model reads, so reusing chatml() here would be a different input. state is parsed as ordered JSON because upstream preserves the request's key order.

Converting a d3 pack (engine #796) is tools/safetensors_to_q4nx.py pack <pack> <model dir> --arch qwen3_5 (the arch is detected from the pack's language_model.* names, so auto is enough). It is not a rename job: three transforms in the pack's GDN tensors are silently wrong answers when they are wrong, so each is named here and covered by a known-answer test (ctest safetensors_to_q4nx):

from to transform
linear_attn.A_log linear_attn.ssm_a -exp(A_log), F32 — the forward computes expf(ssm_a * softplus(dt)), so the raw A_log decays backwards
linear_attn.conv1d.weight [CD,1,CK] linear_attn.ssm_conv1d.weight transpose to tap-major [CK,CD]: the forward indexes conv[j*CD + c]
linear_attn.in_proj_a/b ssm_alpha_proj/ssm_beta_proj rows zero-padded to 32 so they tile; the forward dequantises at the stored height and keeps the first NVH rows (q4_1 where the FLM config asks Q8_0 — a deviation verify measures rather than hides)

The remaining names come from configs/q4nx/qwen3.5_0.8b.json's q4nx_name column (in_proj_qkv → qkv_proj, in_proj_z → self_attn.gate_proj, out_proj → ssm_out_proj, dt_bias → ssm_dt.bias), and visual.* is skipped because the forward runs the text path. Two converter rules exist because of measured load failures, not style: the embedding keeps its 2-D shape (the loader reads vocab and hidden off shape[0]/shape[1]), and text_config's keys are lifted to the top level, because the engine reads config.json at depth 1 only. A tensor with no mapping is a refusal, never a dropped one.

--dtype bf16 writes the same tensor set with no q4_1 tiles at all (every tensor keeps its source bf16, or the F32 a transform forces; verify reports 0 error rather than a loss). It is the container for measuring, not for serving: it holds the weights fixed so an engine run and a reference run differ only in the forward, and the cost of quantization becomes a separate delta instead of an unexplained one. The d3-lite parity row is measured that way (--dtype bf16 vs the default --dtype auto container, same requests, against the pack's own d3_runtime.py).

What is still missing for a real d3 row is the artifact set — but only for a device row. NPU_INFER_HOST_GEMM=1 opens no device, so it needs no ELF: the backbone loads, answers, and serves as the numeric reference for a geometry whose kernels do not exist yet (this is how d3-lite is exercised before its six designs are built). A device row needs all six — QKV K1024 N5120 (q|gate|k|v, q_proj carries the output gate), O K2048 N1024 (GDN's ssm_out reuses it), GU K1024 N7168, D K3584 N1024, GDN QKV K1024 N6144 and Z K1024 N2048 — and without them the device path stops at forward init failed: … this model's plan needs the QKV kernel "full_i8_QKV_K1024_N5120.elf" … (missing).

Two streams on one NPU#

One process owns the NPU by default: it takes an exclusive flock on /tmp/1bit-npu-device.lock for its lifetime (app/npu_device_lock.h), so a second serve of the NPU route waits instead of contending. That is a policy, not a hardware limit -- the driver advertises 16 hardware contexts on this part (hwctx_limit = 16, drivers/accel/amdxdna/npu4_regs.c) and only refuses the 17th -- and the policy stays the default because a second stream buys much less than 2x:

  • The DMA engine is shared. Decode reads the model's int8 weights once per token (~24.3 GB at ~2.2 GB/s effective on the 27B, engine#587); two streams split that bandwidth instead of doubling it.
  • The weights are not shared. Each stream packs its own copy of every layer's weight BO from the model file, plus its own KV cache and scratch, so N streams cost N x the model's device footprint. The NPU's memory is the box's own LPDDR5X, the same pool the CPU and the iGPU draw from, so two 27B streams do not fit.

With that said, two streams do run, and the option is what says you meant it:

# stream 1 of 2, then stream 2 of 2, in two shells (different ports, same model)
./1bit serve -m <NPU model dir> --device npu --npu-streams 2 --port 8000
./1bit serve -m <NPU model dir> --device npu --npu-streams 2 --port 8001

--npu-streams N (1..16, default 1) is forward-serve's flag too: N = 1 keeps the exclusive lock, N >= 2 takes a shared lock, so the opted-in streams co-exist while any exclusive holder -- an unflagged 1bit serve, the per-process ELF runner (npu_engine_universal), another build's serve -- still keeps them all out, in either order, because they share one file and one flock(2).

The lock is one file and one protocol, across runtimes, and it is advisory -- that is what makes it usable beside another NPU engine, and what its limits are:

  • Path and modes. /tmp/1bit-npu-device.lock, created 0644 if absent, flock(2) (not fcntl) so it works across processes, users and runtimes on the box. LOCK_SH = "I am one of N streams, do not wait for other shared holders"; LOCK_EX = "I want the device to myself". A holder keeps its fd open for the life of the process; closing or exiting releases it. LOCK_EX and LOCK_SH never overlap, in either order, on one file.
  • Who may take what. Anything that honours the file interlocks with us: our serves (--npu-streams decides which mode), the ELF runner (LOCK_EX, always). A foreign NPU runtime -- Lemonade's ryzenai-llm backend on Windows, an ONNX session, a benchmark -- may take LOCK_EX to keep us out, or LOCK_SH to be one of the streams. Nothing forces it: a runtime that ignores the file is not slowed, not blocked and not detected.
  • What happens when the other engine ignores it. A runtime that skips the file is not blocked and not detected, so it shares the device exactly the way a co-ordinated second engine does — and that cost is measured: two engines on the shared lock lose 59 % of their aggregate throughput (the table below). The failure mode is slow, not wrong; there is no run on this box that measures an unco-ordinated second engine apart from that, so nothing more specific is claimed here.

Partitioning, and what it would take. Two whole-array streams share one DMA engine, so they serialise; the September prototype that scaled (~100 % each) did it by giving each stream a disjoint half of the columns, which halves per-stream weight reuse, and its xclbin pair is ABI-stale at this pin, so nothing in this tree can select a column split today: both of our instances run whole-array. What each engine costs is therefore the whole model per stream -- one hwctx and one complete copy of the weight BOs, plus its own KV cache and scratch, and the device's hwctx limit is 16. The accounting per engine is: streams x (weights + KV + scratch) must fit in the NPU's share of the box's LPDDR5X alongside whatever the other engine has already allocated, and both engines pull from the same DMA bandwidth. Two different models resident at once (the reason the second engine exists) is therefore bounded by memory first, not by hwctx: see the table below.

A model directory repacked from an FLM pack still carries FLM's own parameter map and version in config.json -- for Qwen3-0.6B, addr_qk 9216, addr_kv 33792, addr_kk 45056, addr_l_begin_mha 53760, addr_l_end_mha 25088, plus flm_version 0.9.22. Those are offsets into FLM's program layout for the AIE programs that live in the FLM install, not a description of this engine's memory: this route reads only the geometry keys (hidden_size, num_hidden_layers, num_attention_heads, num_key_value_heads, intermediate_size, vocab_size, head_dim) and finds its own full ELFs under --kernels, which is why a model directory's npu/ subdirectory is empty on purpose and why addr_* must not be used to reason about what this engine allocates.

What it measures. max_tokens 8, temperature 0, three reps per arm with rep 1 dropped as warm-up (the first request after a load is ~2x the steady state), wall clock per request, each model measured alone with the other not even loaded (strixhalo 2026-10-30, engine 38e29a2, binary b78868c, kernels ~/lb/lfm2-npu/kernels_m16, run ~/lb/612-npu-streams-20261030T112326Z):

run solo both at once per stream aggregate
Qwen3-0.6B + Qwen3-4B, --npu-streams 2 (b78868c, 2026-10-30) 5.79 s / 25.08 s 16.99 s / 35.61 s 34.1 % / 70.4 % 0.41x

That row is the one the second engine exists for: two different models resident at once, each keeping its own weights and its own hwctx, both answering, with no lock bypass. Throughput gets worse -- 0.41x, i.e. running the two back to back is 2.4x faster than running them together -- because two whole-array streams share one DMA engine: the per-token times add up (0.72 + 3.13 s solo per token = 3.85 s; concurrent rounds take 4.45 s) plus about 16 % of handoff overhead. The small model pays most (34 % of solo) because it is latency-bound; the 4B keeps 70 % because its token cost is its own 3.3 GB weight stream, which it would have spent anyway.

So co-residency buys availability, not throughput: each model keeps answering while the other is loaded, instead of a 25-30 s reload. For a short answer, reloading still beats sharing the device -- that is the trade, and it is why the exclusive default stays.

tests/npu_device_lock_test.cpp (ctest npu_device_lock, in CI) proves the lock discipline without a device: exclusive excludes everything, three shared streams co-exist, and an exclusive waits for the last one to go.

The row this exists for. On Linux the two engines are two instances of this runtime on two different models at the same time -- "all NPU models at once" -- and that is what tools/showcase-612-npu-streams.sh measures with MODEL and MODEL_B (default Qwen3-0.6B and Qwen3-4B, whose kernel sets are on this box): each model solo, then both at once, three reps, every number stamped with the build that produced it.

Add-on routes#

The engine keeps a hook for closed-source NPU add-ons (npu/private_route.h). Qwen3.6-35B-A3B (model_type qwen3_5_moe) runs on the NPU through one, experimentally; it is not in this repository and not in a release.

  • -DONEBIT_NPU_PRIVATE=<add-on checkout> (with -DONEBIT_NPU=ON) builds that checkout's addons/ into 1bit. It must define the target onebit_npu_private, which holds register_private_addon(); 1bit calls it at startup.
  • The add-on registers a route per model_type (whether it can serve a directory, and a session that generates from token ids) and may register 1bit subcommands. 1bit serve uses the route for that model type; --npu-opt KEY=VALUE passes options through to it.
  • A route can be optional: an opt-in route for a model_type the engine also serves. When it declines a directory (its unavailable() gives a reason), the engine serves the directory exactly as it would without the add-on.
  • Without the add-on, 1bit serve -m <35B dir> --device npu exits saying the route is not part of this build.

An add-on may also register an encoder for the Laya router (laya/encoder.h, Laya router). tests/npu_private_route_test.cpp (ctest npu_private_route, in CI) checks the registry and that message.

The runtime#

The engine reaches the NPU runtime only through its own public header, npu/npu_rt_api.h: the calls the engine's NPU code makes, each class an opaque handle. The runtime itself is not in this repository; a build from this repository alone has no NPU lane. ONEBIT_NPU=ON takes one of:

# the public binary drop (docs/releases.md, "The public binary drop")
cmake -B build -G Ninja -DONEBIT_HRX=ON -DONEBIT_NPU=ON -DONEBIT_BINARY_DROP=<drop dir or URL>
# a prebuilt runtime library that implements npu/npu_rt_api.h
cmake -B build -G Ninja -DONEBIT_NPU=ON -DONEBIT_NPU_RT_LIB=<path>/libnpu_rt_api.a
  • ONEBIT_NPU_HOST (the model reader, Q4NX, packing, the tokenizer) needs no runtime and builds everywhere, including public CI, where its tests run.
  • The release builds the runtime from a pinned commit named in config/npu-runtime.config (Releases).

The NPU needs the amdxdna kernel driver. third_party/xdna-driver pins upstream amd/xdna-driver as the driver version the engine is checked against (the kernel's own copy also works); nothing from the pin is built into or shipped with the release. .github/workflows/bump-xdna.yml moves the pin when run by hand, because a driver move means rebuilding the module on Strix Halo and checking the NPU there first.

The MTP head (FastFlowLM's container -> ours)#

tools/flm_head_import (built as flm-head-import) turns a FastFlowLM MTP-head container (model.mtp.q4nx) into a sidecar directory of ours. The head is one Qwen3.5 full-attention layer plus an input fusion; the base model keeps its embedding, lm-head, tokenizer and RoPE, so this artifact is only the head.

The container is safetensors-shaped and its quantised tensors are rank-3 [nrb, ncb, 4736] with dtype "I8". That 4,736-byte cell is our Q4_K chunk: u8 scale[g*32+n] at 0, u8 min[g*32+n] at 256, nibbles at 512 (byte k*16 + n/2, even n in the low nibble), bf16 S[n] at 4608, bf16 M[n] at 4672, and w = q4 * (scale*S) + min*M. Measured, not assumed: q4nx::dequant_tile(Chunk::Q4K, …) reproduces FastFlowLM's own decoder bit for bit on six cells recorded from six of the head's matrices (tests/golden/flm-i8, floats recorded from their published library; the layout facts are in amd-oss/npu-re docs/FACTS-flm-q4nx-container-and-mtp-head.md). Two things follow, and they are the reason this tool is small:

  • the default form copies every cell unchanged — no requantisation, nothing to lose, and the import self-check re-decodes each matrix from the source and from the copy and compares;

  • the alternative --form q4_1 writes our mode-1 chunk (5,120 B: bf16 S[256], bf16 M[256], 4,096 code bytes, w = code*S + M) through q4nx::q4k_to_q4_1, whose only loss is rounding S*scale and M*min to bf16. The tool prints that factorisation error rather than hiding it (measured on the 27B head: 0.67 % of values unchanged, max |delta| 1.2e-3, mean |delta| 6.8e-5).

    flm-head-import model.mtp.q4nx -o head-q4k # cells copied unchanged flm-head-import model.mtp.q4nx -o head-q4_1 --form q4_1 # our mode-1 chunks

tools/flm_head_pb16i.py writes the third form, the pb16i image (npu/forward/include/q4nx_pb16i.h), and it is the one form this head cannot have exactly: pb16i carries one int16 magnitude per (32 K, column) with no per-group bias, while the source blocks are asymmetric (w = q4*S + M) and their magnitudes span about 100x inside a column, where an int16 with an 11-bit mantissa allows about 16x. Forcing it costs a measured 11-18 % relative L1 residual, so the mode-1 or Q4_K forms are the ones to run; the script keeps the measurement next to the images it writes.
