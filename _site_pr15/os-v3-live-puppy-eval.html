Puppy as the base of 1bit OS v3: evaluation#

The owner's direction (2026-11-01): build 1bit OS v3 on Puppy Linux instead of Ubuntu Server — Puppy for both roles, the live/try stick and the installed system (frugal install on the NVMe with a persistent save layer), headless, with our kernel and our drivers, not the distribution's.

This page is the measurement, and the recommendation. Everything below is measured on strixhalo (2026-11-01) or in QEMU here unless it says otherwise; the numbers that are not measured yet say so.

Verdict: adopt, conditional on four blockers — and the conditions are small, each with a measured path. What makes the recommendation, in one line: Puppy already has the two things our BusyBox image cannot grow (a package manager and a persistent layer on the stick) and a save-file model that is #706, at a size the initramfs cannot match; what it does not have is our kernel, and that turned out to be a kernel config gap of about fifteen =y symbols, not a fork.

1. Size and memory, against our initramfs#

Size and time are the honest trade: +850 MB on the stick, +1.2 GB on the installed disk, and +84 s to the first screen (24.5 s → 108.8 s, measured on the same QEMU with the same timestamping) for a package manager, a save layer and a real userland. The c18 number is the boot of the published image as a USB stick (-device usb-storage, which is what the init requires: it refuses a non-removable disk so an internal disk's /data is never taken); the Puppy number is its stock kernel, so the comparison is the two media, not the two kernels. For a 58 GB stick and a 2 TB NVMe that is nothing; for the "100 MB EFI file" promise of today's image it is the whole OS.

2. The kernel is ours, and that is where the work is#

os/v3/puppy/mk-huge-kernel.sh builds woof-CE's kernel package from our own deb tree, so no distribution kernel appears anywhere in the image: vmlinuz-7.3.0-rc4-1bit-perfopt+, and an SFS with /lib/modules/7.3.0-rc4-1bit-perfopt+ (3819 modules, .ko.xz as Ubuntu ships them, loaded by the kernel's own xz decompressor), /lib/firmware/{amdgpu,amdnpu,rtl_nic} and a marker etc/1bit/kernel with the image's sha256 and each out-of-tree module's signer. The script refuses a module built for another kernel or an unsigned one (modinfo -F vermagic / -F signer), which is the os/mini lesson applied to a second consumer.

Blocker 1: the kernel config#

Puppy's initrd mounts the medium and layers the save file itself, before any module can be loaded. Our kernel is Ubuntu-shaped: almost everything is =m. Measured, ours against Puppy's own stock kernel 6.8.12 from kernel-kit:

knob ours Puppy's stock
BLK_DEV_SR (the CD) =m =y
BLK_DEV_SD / BLK_DEV_NVME (stick, frugal disk) =m =y
ISO9660_FS =m =y
SQUASHFS (XZ and ZSTD decompressors =y on both) =m =y
OVERLAY_FS =m =y
BLK_DEV_LOOP (a save file is a filesystem in a file) =m =y
EFIVAR_FS =m =y
FAT_FS/VFAT_FS + NLS_CODEPAGE_437/NLS_ISO8859_1 =m =y
EXT4_FS, USB, USB_XHCI_HCD, USB_STORAGE, HID_GENERIC, USB_HID =m =y
DEVTMPFS_MOUNT not set =y
DRM_SIMPLEDRM not set =y
AUFS_FS absent absent (Puppy uses overlay — so do we)

os/v3/puppy/kernel-puppy.fragment is exactly that list, with our current value beside each line. It is a config fragment, not a patch: our kernel keeps every perfopt and driver decision it has, and the weekly kernel build appends the fragment before make olddefconfig. The cost is one kernel rebuild and a new A-phase gate; the risk is that a =y symbol pulls something into the image that was not there, which is what the boot gate measures.

One thing the first version of the fragment got wrong, found by reading our own config rather than by a build: a tristate cannot be =y while a symbol it depends on is =m, and make olddefconfig does not refuse — it silently reduces the child back to =m. Ours are =m all the way down (SCSI, SCSI_MOD, SCSI_COMMON, CDROM, ATA, SATA_AHCI in /boot/config-7.3.0-rc4-1bit-perfopt+), so BLK_DEV_SR=y on its own would have built a kernel that still could not read the ISO, with nothing in the build output saying so. The fragment now carries the chain above the drivers (24 symbols, from 20), and the per-symbol grep -qx "$sym=y" check in os/v3/puppy/README.md is what makes that class of mistake loud.

Until that fragment is in a built kernel, the Puppy base cannot boot on our kernel at all — measured twice, and the second time on the real artifacts rather than on a borrowed initrd: the built ISO's own initrd.gz (2,369,371 B, 127 cpio entries, from initrd-progs) on the ISO's own vmlinuz (7.3.0-rc4-1bit-perfopt+) stops with

Waiting 5 seconds for slow storage devices [0/5] ... [4/5].
Finding puppy main sfs file. failed
  3: PSUBDIR= P_BP_FN= P_DEF_FN=puppy_upup64r_26.04.sfs
  HAVE_PARTS=''      TRY_PARTS=''
  6: ONE_PART= ONE_TRY_FN= PDRV=
***  /puppy_upup64r_26.04.sfs not found.
*** Error is too critical, dropping out to console...  ~ #

HAVE_PARTS='' is the part worth reading twice: the init did not fail to mount the medium, it found no partitions at all — no /dev/sr0, because sr_mod is a module and an initrd that cannot load modules has nothing to read the ISO with. That is precisely the first block of the fragment (BLK_DEV_SR, ISO9660_FS, BLK_DEV_SD, BLK_DEV_NVME, USB_STORAGE) set to =y.

3. Blocker 2: the binaries need glibc 2.43, so the base must be 26.04#

Measured on the c18 release tarball, with readelf -V:

binary highest versioned symbol
1bit (the engine) GLIBC_2.43
lemond (Lemonade) GLIBC_2.43
llama-server (HRX) GLIBC_2.34

Puppy noble64's libc.so.6 defines at most GLIBC_2.39 (read from the extracted SFS). So on a 24.04-based Puppy, llama-server would run and 1bit/lemond would not: the appliance's two entry points are exactly the two that fail. woof-CE has a resolute64 recipe (Ubuntu 26.04, glibc 2.43, "DISTRO_NAME='ResolutePup64'", SFS compression xz, package manager apt/Synaptic per its release notes), which is the base this evaluation builds. That recipe is not in woof-CE's CI matrix — only ubuntu-noble64 and ubuntu-jammy64 are — so a resolute Puppy is ours to build, and that is what os/v3/puppy/build.sh does.

Blocker 4: the 26.04 base and what it carries#

From the noble64 SFS (measured by extraction) and ResolutePup64's own release notes, against what #706/#704 and the appliance want:

need noble64 build resolute64 recipe (per its notes) what v3 must add
package manager dpkg + PETget, no apt binary built here: dpkg + PETget, no apt either (the recipe's own notes claim apt/Synaptic; the built rootfs has /usr/bin/apt absent — measured) ship apt if "updates from the Ubuntu feed" is the promise
python3 yes (3.12) yes — (turns release-check's sealed-sig row from SKIP into a check)
efivarfs kernel =y recipe uses the same built-in shape our kernel: fragment above
efibootmgr yes, /usr/bin/efibootmgr yes (dpkg) — (engine#709's tool is there)
mokutil no no ship it (mokutil or our own enrol step) for Secure Boot
sshd no (ssh client only) no ship openssh-server, keys carried from the stick
persistent layer on the stick (#706) pupmode 5/12/13, save file or folder — the initrd's own machinery (sbin/load_ext_file, validate_pupsave_upgrade) same size it (psave=/pupsave) and document it as the answer to #706
release identity (#704) none none /etc/1bit/release-identity, written by our package/first boot
headless first-run wizard asks keyboard/locale/X even with pfix=nox same pre-answer it (/etc/rc.d/rc.local hook or a seeded PUPSTATE)
user model root only, no onebit user, no sudo model same decide honestly: run as root and say so, or add a user + su/doas; Puppy's tools assume root
X11 baggage X.Org, GTK3, JWM, Roxfiler, Palemoon (~1 GB unpacked) same not started when headless (pfix=nox), but it is on the disk

That table is the real cost of the Puppy plan: the appliance's identity (a user, sshd, mokutil, a release identity) is four packages and one seeded first boot, and the "headless" promise is one flag plus one pre-answered wizard — but the root-only model is a design decision, not a package.

5. Secure Boot: what the Puppy medium has, and what ours has to be#

The noble64 ISO's EFI/boot/ carries bootx64.efi, grubx64.efi, mmx64.efi — a shim + grub + MokManager chain, so a Puppy medium can boot with Secure Boot on in principle. Our kernel is signed by our MOK (CN=strixhalo Secure Boot Kernel), which a stock Puppy chain does not have in its db/MOK, so the v3 medium replaces the chain with the one os/mini and os/v2 already boot: shim (Microsoft-signed) → our MOK-signed grub → our MOK-signed kernel → our modules. The measurement that matters and is not done yet: booting the swapped medium with OVMF Secure Boot on, then enrolling our MOK once in MokManager (the same one-keyboard-step the Ubuntu plan documents). It is the same chain, the same key and the same step as today's image, on a different initrd.

6. What Puppy gives that our initramfs cannot#

  • A package manager and an update path on the medium itself: a stick that can be repaired and extended (apt/PETget) rather than reflashed.
  • A persistent layer that is #706's answer, with a decade of save-file handling (load, upgrade, validate) and the choice of save file in a folder or inside a file — the initrd already implements the hard part.
  • A real userland on the try-it medium: python3, bash, git, editors, so the stick is a rescue system too, and 1bit-release-check can run its full row set (its sealed-sig row needs python3, which the c18 image SKIPs for exactly that reason — measured in the gate log).
  • Frugal install: the same SFS + save layer boots from the NVMe, with the OS read-only and the save layer writable — the "installed Puppy" mode the owner asked for, without an installer writing a rootfs at all.

The build, and where it stands#

os/v3/puppy/build.sh is woof-CE's CI recipe (build.yml) as one command, in a throwaway container, with two things it does not say out loud and this evaluation found the hard way:

  1. merge2out refuses to run when the host is not a running Puppy unless GITHUB_ACTIONS is set — CI sets it, so a container build must too (otherwise the build stops at "you will still need to download a Puppy ISO and devx sfs" and looks like a hang);
  2. 3builddistro takes the kernel from woof-out_*/kernel-kit/output/ and otherwise downloads a stock Ubuntu kernel — our huge tarball has to be dropped there, which build.sh does.
